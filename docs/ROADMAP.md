# Roadmap

## Confirmed decisions (from planning discussion)

- **Auth migration self-clears old data instead of requiring a manual DB wipe (post-Milestone 10 fix):** the migration originally assumed the database was empty, per the confirmed decision that pre-auth test data didn't need preserving — but it never actually enforced that, so it crashed with a `NOT NULL constraint failed` on any real database that still had vocabulary/review/writing data in it (i.e. any database that had actually been used). Compounding this: SQLite's DDL isn't transactional, so the partial failure left the `users` table committed while Alembic's version tracking didn't advance, and every retry crashed immediately trying to recreate `users`. Fixed by making the migration check for existing tables/columns before creating them (safe to retry from any partial state) and explicitly clearing the three affected tables before adding their `NOT NULL user_id` column, rather than relying on the database already being empty. Verified against both a fresh database and a reproduction of the exact broken state this produced in practice.
- **Second round of the same migration issue (post-Milestone 10 fix #2):** a follow-up retry hit a *different* leftover artifact — SQLite's batch-mode alter creates a `_alembic_tmp_<table>` scratch table internally, and an interrupted attempt (container restarted mid-batch, across a couple of real retries) left that scratch table behind, so the next retry crashed trying to recreate it. This is a distinct failure mode from the `users`-already-exists case above — same underlying cause (SQLite DDL isn't transactional, so partial progress within a single migration attempt persists across restarts), but a different specific leftover. Fixed by explicitly dropping any stale `_alembic_tmp_<table>` before each batch-alter, making the migration safe to retry from any intermediate state a real interrupted run could leave behind, not just the ones anticipated by the first fix. Verified with a dedicated reproduction of this exact leftover state, for all three affected tables.

- **Config robustness (post-Milestone 10 fix):** a mistyped variable in `backend/.env` (`google_client_secrect` instead of `secret`) crashed the entire backend on startup with `extra_forbidden`, even though nothing in the code reads that variable at all. Root cause: pydantic-settings enforces `extra="forbid"` by default specifically for values loaded from an actual `.env` **file** — plain OS environment variables are handled differently (silently ignored if unrecognized), which is why this wasn't caught by an earlier test that only checked the shell-env-var path. Fixed by setting `extra="ignore"` explicitly in `Settings.model_config`, with a regression test covering the file-based path specifically. Lesson for future settings changes: always test the `.env`-file-loading path, not just constructing `Settings()` with env vars set directly.

- **Docker + new npm packages (post-Milestone 10 fix):** `docker compose up --build` alone does not pick up a new npm dependency, because `frontend_node_modules` is a named volume (added in Milestone 6 to prevent host/container platform mismatches) whose old content persists across image rebuilds regardless of `package.json` changes. Whenever a milestone adds an npm package, `docker compose down -v` is required before `docker compose up --build` to force a real reinstall. Backend Python packages don't have this problem — no persistent volume shadows them, so `--build` alone is sufficient there. Documented in the main README's day-to-day section.

- **Database:** SQLite for local dev, but the app reads `DATABASE_URL` from environment config everywhere — switching to Postgres later is a one-line `.env` change, no code changes.
- **Dashboard:** pulled forward to Milestone 2, right after the proof of concept.
- **Docker:** added in Milestone 6, dev mode with hot reload — now the primary way the project runs day-to-day. Manual venv/npm setup still works and is what CI uses.
- **AI provider:** OpenAI, confirmed in Milestone 5. Both AI features (Grammar Tutor, Writing Coach) go through the same `AIProvider` abstraction, so adding Claude/Gemini later doesn't touch feature code.
- **Writing Coach (Milestone 7):** corrections come back as a structured, itemized list (original → corrected → explanation, each tagged "grammar" or "wording") rather than freeform prose — via OpenAI JSON mode. Every submission is saved to a `writing_submissions` table. Suggested vocabulary has a one-click "+ Add to my vocabulary" button.
- **Reading Helper (Milestone 8):** fully frontend — "unknown" is determined purely by checking pasted text against the existing Vocabulary Manager list, client-side, no backend changes. No AI, no dictionary API — definitions are manual-entry only, matching the original brief's "no AI required" note for this feature. Already-known words are also clickable, showing a read-only view of what's saved.
- **Verb-form recognition (post-Milestone 8 fix):** a new `POST /verbs/lookup-batch` endpoint reuses the Milestone 4 conjugation engine in reverse — given raw words, it finds which ones are conjugated forms of a known verb. This powers three things: (1) Reading Helper highlighting now treats a conjugated form of an already-known verb as known, not a separate unknown word; (2) saving a recognized verb form saves the infinitive, grouping all conjugated forms under one vocabulary entry instead of creating duplicates; (3) Vocabulary entries that are verbs are now clickable through to the Verb Explorer's conjugation page, which shows a "Back to Vocabulary" link instead of the default "Back to Verb Explorer" when arrived at that way (tracked via React Router `location.state`).
- **Production-readiness (Milestone 9):** the deploy target is Render (backend + managed Postgres) + Vercel (frontend), chosen for real free tiers and name recognition. AI rate limit set to 10 requests/day/visitor (identified by IP, no login system) — deliberately conservative for the first deploy, and built as a per-request env var read (not baked in at import time) specifically so it's a one-line change with no code touch later.
- **CORS config fix (post-Milestone 9):** `cors_origins` had to be changed from a `list[str]` field to a plain `str` field with the parsed list exposed via a property. Pydantic-settings tries to JSON-decode any list-typed field's raw env value before any custom validator runs, so a plain comma-separated value (valid per our own docs) crashed the app at startup. Root-caused and fixed; all four input shapes (comma-separated, JSON list, multiple origins, unset/default) verified working.
- **Deployment decoupled from the milestone sequence:** more features first, deploy "whenever ready" rather than as a fixed next step — see `DEPLOYMENT.md` for the runbook when that time comes.
- **Post-Milestone-9 feature order:** Real Accounts/Login moved to be first among the remaining features (originally 3rd in initial preference) — Progress Analytics, Sentence Mining, and Anki export all touch Vocabulary/review data that should be scoped per-user once login exists, so building auth first avoids retrofitting user-scoping into each of them afterward.
- **Auth method (Milestone 10):** Google Sign-In only, no email/password — confirmed free and reasonably easy to set up (one-time Google Cloud Console configuration for a Client ID), and avoids building/maintaining password storage, reset flows, and verification email delivery. The backend never sees a password; it verifies Google's ID token and issues its own JWT for subsequent requests.
- **Access model:** Grammar Reference and Verb Explorer are fully public, no login required to browse. Vocabulary, Flashcards, Dashboard, Writing Coach, and Reading Helper all require login (Reading Helper wasn't in the original example list but was included since it's built entirely on the user's own vocabulary data). The Grammar Tutor is embedded on an otherwise-public Grammar page — the article stays visible, but the chat panel itself is gated.
- **Migration approach:** existing local data was wiped rather than migrated to a default user (confirmed acceptable — it was test data). The `users` table and `user_id` columns were added in one migration using Alembic's batch mode, which is required for SQLite (the local dev default) to add a foreign-key constraint to an existing table — this was caught as a real bug during testing (the naive autogenerated migration works on Postgres but crashes on SQLite) and fixed before shipping.
- **Rate limiting keys:** switched from IP-based to account-based for the Tutor/Writing Coach endpoints now that both require login — more correct than IP, since a shared IP (university network, household router) would otherwise share one quota across multiple real people.

## Future direction: immersion mode (noted, not scheduled)

A real long-term goal: the permanent UI chrome (nav labels, buttons, page headers — the text that's always on screen, not the study content itself) should eventually default to Portuguese with hover-to-translate, rather than always being English. The reasoning: thinking in the target language, not constantly translating, is one of the more effective ways to actually learn it — a UI that's always in English works against that. Not being built now; likely needs its own milestone to decide implementation (a translation-string system, a toggle to fall back to English, and a decision on which specific parts — if any — should always stay English on purpose). Keeping it recorded here so it isn't lost.
